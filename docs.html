Attendance System — Developer Notes

Static implementation guide for this FastAPI + ZKTeco collector. Generated from the current repository structure; it intentionally does not contain credentials or database connection strings.

System at a glance

API

main.py creates the FastAPI app, applies CORS, creates mapped tables at startup, and mounts the attendance, summary, leave, and voucher routers.

Attendance database

database_url backs raw attendance, derived summaries, and vouchers. Its session dependency is get_db.

ePortal database

database_url2 is the source for emp_list and leave_app. Its session dependency is get_db2.

Device collectors

cron.py, cron2.py, cron1108.py, and cron806.py read ZKTeco logs, classify punches, then call the API over HTTP.

Primary flow

ZKTeco device → collector script → POST /attendance/ → eportal_attendance → POST /summary/ or /summary/cron/ → attendance_summary → leave overlay / voucher workflows

Scheduled collector behavior

What fetches from the device: no FastAPI service calls ZKTeco in the deployed API route. The standalone collector scripts cron.py, cron2.py, cron1108.py, and cron806.py instantiate zk.ZK, connect to the configured device, disable it, call conn.get_attendance(), then re-enable and disconnect it. They send the prepared payload to POST /attendance/. The API-side attendance_service.batch_insert_update_logs() persists that payload; summary_service, leave_service, and voucher_service work from database records rather than from the device.

  • Collectors disable a biometric device while reading all logs, retain a lookback window (currently one day in the runnable blocks), identify punch 0 as time-in and every other punch as time-out, then re-enable/disconnect.
  • The first time-in is retained; later time-out punches replace the saved time-out. The payload is grouped as { employee_id: { YYYY-MM-DD: punch_data } }.
  • The API upsert only changes time-out, checkout status, and undertime for an existing employee-day. It preserves the original time-in, status, and lateness.
  • Current attendance rules are embedded in the collectors: regular 09:00–18:00, Friday 17:00/17:30 variants, Saturday 17:00, and Half Day thresholds. The 15:00 voucher target is inactive while vouchers are disabled. Treat these as business rules, not generic device logic.

Time-log classification rules

RuleCurrent collector behavior
Time-inBefore 09:01: On time. From 09:01 to before 11:00: Late, with minutes measured from 09:00. From 11:00 onward: Half Day; arrivals after 13:00 retain a lateness value measured from 13:00.
Regular time-outTarget is 18:00. A checkout before the target is Undertime with the minutes short; at or after target is On time.
Friday time-outA time-in before 08:01 sets a 17:00 target. A time-in from 08:01 through 08:30 sets 17:30. Otherwise the regular 18:00 target remains.
Saturday time-outTarget is 17:00, or 15:00 when a voucher is already associated with that attendance record. Voucher checks happen only for an early Saturday checkout.
Half-day checkoutIn the current changed collector rules, a time-out at or before 13:30 is marked Half Day and does not store undertime minutes.
Missing/incomplete dataA time-out before any saved time-in is ignored. A new employee-day without a time-in is not inserted. Existing records can later receive a time-out through the upsert.
Rule source: these values are duplicated in collector scripts. The currently modified cron2.py uses the 13:30 half-day threshold and inclusive Friday minute boundaries described above; review it with HR before copying its behavior elsewhere.
Schedule explicitly: this repository does not configure Windows Task Scheduler, cron, Docker, or a service manager. Define one authoritative production schedule and log success/failure outside these scripts.

Developer notes and review findings

Fix before exposing beyond a trusted internal network: main.py enables credentialed CORS with wildcard origins. Browsers reject or mishandle this combination, and it is unsafe as an access policy. Use an explicit allowlist, HTTPS, and a stronger identity/authorization model than one shared API key.
PriorityFindingDeveloper action
HighRouters wrap broad exceptions and return raw exception text in HTTP 500 responses.Log a correlation ID and server-side exception; return a stable generic client error. Do not expose database, device, or internal HTTP details.
Highuse_multiple_vouchers updates an attendance record and voucher without validating ownership, expiry, unused state, attendance status, or an existing voucher assignment.Reuse the validation rules from the single-voucher path and make the bulk operation atomic and idempotent.
Highcheck_voucher indexes the result of .first() without checking for no matching attendance record.Return false when no row exists; otherwise an unrecognized employee-day produces a server error.
MediumSummary creation performs a query per candidate summary row and its result serializer assumes every summary employee exists in emp_list.Batch-load existing keys and handle missing employee master data so one stale ID cannot fail an entire page.
MediumType consistency is uneven: date/time query parameters and body fields are often strings; integer/date columns are searched with ilike.Use Pydantic date/time fields and typed FastAPI query parameters; validate page/page_size bounds.
MediumLeave overlay only changes summaries that already exist; it skips Sundays but does not apply an employee’s work schedule or a holiday calendar.Confirm that behavior with HR, then centralize calendar/schedule policy before changing reporting results.
MediumVoucher generation contains a hard-coded Cebu employee-ID exclusion list.Move eligibility rules to configuration or an explicit employee attribute, with an audit trail.
LowSeveral collectors duplicate near-identical logic. cron2.py has uncommitted rule changes, while cron806.py has the same current content hash as it.Choose a single tested collector module and pass device configuration as arguments. Preserve the current business-rule change until HR validates it.
LowEmployee2 declares created_at twice, so the latter declaration wins in the ORM mapping.Correct the model only after comparing it to the live ePortal schema; this source table should not be altered accidentally.

Safe local development

  1. Create and activate a virtual environment, then run pip install -r requirements.txt.
  2. Copy/configure a local .env with non-production database and device endpoints. Never commit it.
  3. Run uvicorn main:app --reload. This imports the models and may create missing mapped tables, so point it only at an approved development database.
  4. Use http://127.0.0.1:8000/docs for authenticated endpoint checks. Do not run collector scripts against a production device while developing rules.
  5. Before release, run python -m compileall -q -f ., exercise each write path with isolated fixture data, verify summaries after the collector and leave runs, and check Task Scheduler/service logs.

Optional Cloudflare backup flow

The D1-only backup scaffold is now included under cloudflare_d1/:

ZKTeco → collector → POST /attendance/ (primary) → Attendance DB
                             ↘ HTTPS backup endpoint → Cloudflare Worker → D1 (attendance_events)
  • Keep the existing Attendance API as the operational source of truth. A temporary Cloudflare outage must not prevent local collection or primary attendance storage.
  • cron_d1_backup.py archives every unprocessed device punch in attendance_raw_events. Its device UID is the entry identity and input-order key; the timestamp, punch code, and other ZKTeco fields are retained as source data only. The processed daily D1 backup table is intentionally not used.
  • Put Cloudflare credentials in the Worker secret store; do not put a Cloudflare API token in the collector’s .env. Authenticate collector requests with a dedicated shared secret or HMAC signature.
  • The backup request is best-effort and is intentionally isolated from the primary insert. A failed request is printed by the collector; it is not yet a durable retry queue.
  • cron_d1_backup.py is an optional independent collector: it reads configured ZKTeco devices concurrently over separate device connections, then sends only to D1, never to POST /attendance/. Keep the existing D1_BACKUP_DEVICE_IP/D1_BACKUP_DEVICE_PORT and D1_BACKUP_DEVICE_IP_1108/D1_BACKUP_DEVICE_PORT_1108 pairs. Configure ONE CENTRAL only with D1_BACKUP_OC_DEVICE_IP and D1_BACKUP_OC_DEVICE_PORT; configure CEBU only with D1_BACKUP_CEBU_DEVICE_IP and D1_BACKUP_CEBU_DEVICE_PORT. The collector fixes OC to D1_BACKUP_URL2 and CEBU to D1_BACKUP_URL3; each has its own matching token. The older D1_BACKUP_DEVICE_*_OC/_CEBU variables remain accepted only for compatibility. Use D1_BACKUP_DAYS for the retention window.

Deploy the Worker

  1. From cloudflare_d1/, use wrangler.toml for the primary database, wrangler.oc.toml for ONE CENTRAL, and wrangler.cebu.toml for CEBU. OC/CEBU must be deployed while authenticated to the accounts that own their separate D1 databases.
  2. For a new database, apply schema.sql. For an existing raw-events database, apply migrations/0003_device_uid_identity.sql after the biometric UID column is present; it backfills UIDs and replaces the device-UID index with a unique one.
  3. Set the Worker secret with npx wrangler secret put BACKUP_TOKEN, then deploy with npx wrangler deploy.
  4. Set the collector environment values ENABLE_D1_BACKUP=true, D1_BACKUP_URL=https://<worker-host>/raw-attendance-events, and the same D1_BACKUP_TOKEN. Set D1_BACKUP_DAYS=all only when backfilling every activity retained by a device; otherwise use a bounded lookback. Test /health and one fixture batch before scheduling production collectors.

npx wrangler d1 execute DB --remote --file=schema.sql --config wrangler.oc.toml

npx wrangler d1 execute DB --remote --file=schema.sql --config wrangler.cebu.toml
npx wrangler secret put BACKUP_TOKEN --config wrangler.cebu.toml
npx wrangler deploy --config wrangler.cebu.toml

After each deploy, copy its Worker URL plus /raw-attendance-events into D1_BACKUP_URL2 (ONE CENTRAL) or D1_BACKUP_URL3 (CEBU). If its Worker uses a distinct secret, set the matching numbered token. Then set only the dedicated OC or CEBU device variables in its own block. OC and CEBU must resolve to different IP/port pairs.

If a device connection, configuration, or Worker upload fails, the collector writes a timestamped error (including the site/connector, device endpoint, HTTP status, and safe Worker response text) to error.log in the project root. Tokens and authorization headers are never written to that file.

Run the backup cron every five minutes (Windows)

Create a Task Scheduler task whose action runs python.exe cron_d1_backup.py, with “Start in” set to the project directory. Set the trigger to Daily with Repeat task every 5 minutes for 1 day. In Settings, choose Do not start a new instance if the previous run is still running. Run it under an account that can reach both ZKTeco devices and the Worker URL.

schtasks /Create /TN "Attendance D1 Backup (5 min)" /SC MINUTE /MO 5 /TR "C:\Path\To\Python.exe D:\LocalFiles\Desktop\DEV\attendance_system\cron_d1_backup.py" /F

Replace the Python path with the interpreter containing this project’s dependencies. Confirm ENABLE_D1_BACKUP=true, D1_BACKUP_URL, and D1_BACKUP_TOKEN are available to the scheduled task; Task Scheduler does not always inherit the interactive shell environment.

D1 schema error recovery

If D1 reports no such table: main.attendance_raw_events while creating an index, only the index statement was submitted. Apply the complete schema first; it creates the table before either index:

cd cloudflare_d1
npx wrangler d1 execute d1_eportal_attendance --remote --file=schema.sql
npx wrangler d1 execute d1_eportal_attendance --remote --command="SELECT name FROM sqlite_master WHERE type='table' AND name='attendance_raw_events';"

The verification query must return attendance_raw_events. If using the Cloudflare dashboard SQL editor, paste the entire contents of schema.sql in order rather than running an index fragment by itself.

Before production: do not run the independent collector at the same time as another collector against one ZKTeco device; schedule it with an offset because device connections may contend. Confirm retention/privacy requirements and add a durable local outbox if “backup” must guarantee eventual delivery during Cloudflare outages. Do not send an employee’s full personal record when the attendance event fields are sufficient.
